# Weblab v0.7.0

This release adds optional
authentication, role-based access and basic activity records for a shared lab,
with server-published instructions and optional administrator Agent access.
Published v0.6.0 images do not contain these features.

## Optional authentication and roles

Authentication stays off by default. Enable `WL_AUTH=1` and provision three
distinct passwords locally using the [authentication setup](../authentication.md#setup).
There are no default credentials or passwords generated into container images.

| Account | Role | Access |
| --- | --- | --- |
| `admin` | Administrator | Full lab controls, imports/exports, images, topology, instructions and optional Agent |
| `user` | Writer | Console input, node/lab start and stop, and runtime link faults; no topology edits, imports/exports, image uploads or instruction changes |
| `guest` | Reader | View the shared lab, console output, logs and storage; no console input or device/link operations |

Permissions are checked by the server and console transport. Login includes
remembered sessions, logout, expiry and CSRF/origin checks. Server-side password
checks are delayed after three failures; 13 consecutive failed passwords lock
the account. Lockout survives restart and has an environment-based recovery
procedure. See [login delay and recovery](../authentication.md#login-delay-and-account-recovery).

## Console ownership and administrator Agent

- Admin can take over a writer-held console lock immediately. A writer requesting
  an admin-held lock needs approval from the owning admin station. Requests expire
  or cancel on disconnect/ownership changes; same-role takeovers retain confirmation.
- With authentication enabled, the optional Agent is available only to admin.
  Conversations, attachments, approvals and provider sign-in belong to the exact
  Weblab login, not everyone using the shared admin account.
- The Agent may borrow a console lock held by that same login. Browser typing is
  blocked during the console operation; **Take back control** restores input and
  keeps the browser's lock. Normal completion also restores typing. Other logins'
  locks remain protected. Commands already delivered cannot be undone.
- Console-input permissions, exact-action approval or YOLO, fresh reads and
  revision/cursor checks still apply. Loss of access during a send is reported as
  uncertain delivery, requiring inspection before retrying.

**Logging out, replacing the Weblab login or letting it expire revokes its Agent
sessions and deletes their history, attachments and OpenAI sign-in storage.**
Export conversations you want to retain before logging out. Another admin login
remains independent. Writer/reader Agent access and external MCP stay disabled
when authentication is enabled. Without authentication, existing Agent/MCP opt-ins
remain available. The Agent Compose override is still optional.

## Shared instructions and activity records

Admin can open a local Markdown/text preview, then explicitly **Publish** it to
all stations. Opening a file alone does not publish it. Writers/readers receive
the published exercise automatically, and conflicting administrator updates are
rejected. Without authentication, any station in the trusted workspace may publish.

Published instructions survive restart in the lab data directory. They are
**not included in topology JSON or saved ZIP exports**; imports leave them in
place. Keep the original exercise file and publish the matching document after
changing labs. See [instructions](../instructions.md).

Admin's **Activity records** button shows account/session, operation and outcome
for supported browser mutations and Agent tool operations. Records persist for
up to 30 days or 10,000 entries and exclude credentials, prompts, attachments,
document contents and raw console input/output. They do not record human console
commands or lock handoffs, prove device configuration success, or provide a
tamper-proof audit trail. See [coverage and limits](../authentication.md#activity-records).

## Workspace refinements

The **Agent workspace** preset is now named **Split workspace**, reflecting its
use with Instructions as well as Agent. Existing saved layout choices continue
to work. Docked Instructions controls occupy a separate row below workspace tabs,
with horizontal scrolling at narrow widths. The logout control is compact, and
writer/reader selection and unavailable link-delete prompts are corrected.

## Scope

**AAA is an initial implementation under active development.** Later stages are
planned for multiple named users, a live administrator control panel, per-user
node and instruction assignments, and remote test workflows. See the
[development roadmap](../authentication.md#development-status-and-roadmap);
these features are not part of v0.7.0 and have no committed delivery dates.

These are three shared accounts in **one shared lab**, not named users, isolated
student environments or a remote-examination system. All roles can see shared
console output. Writers have real device CLI/PC shell access. Readers are wholly
view-only; restricted `show`/`ping` commands are not implemented. OTP, per-node
assignments, delegated writer Agents and per-person command attribution remain
future work. Use the [documented trusted-group deployment](../authentication.md#deployment-and-state),
with HTTPS for remote authenticated access. Existing device/model limitations
continue to apply.

## Upgrade

1. Save device configurations and export a stopped-lab ZIP. Shut down Junos
   gracefully from its CLI before stopping its process. Keep original instruction
   files and export Agent conversations you need before enabling authentication;
   earlier anonymous Agent sessions are not adopted and are cleaned up.
2. Retain the existing Compose project, image/data mounts and Agent named volumes.
   Do not use `down -v`. Authentication state and activity records live separately
   in `<lab-data>/.auth/`; lab JSON/ZIP exports do not back them up or replace them.
3. Use matching `0.7.0` core (`weblab` or `weblab-exos`) and optional
   `weblab-agent` images under `ghcr.io/weblab-network/`. Source builds require rebuilding/recreating
   the services. Omit the Agent override for a deployment without it.
4. Authentication remains opt-in. Follow [setup](../authentication.md#setup) for
   passwords and cookie settings; recreate the service after environment changes.
   Start/restart affected nodes so their console wrappers load the new lock
   protocol, and reload browser tabs.

## Validation status

The candidate passed 288 disposable backend tests and browser regressions for
authentication, roles, console ownership, published instructions, Agent
isolation/revocation, activity records and workspace controls.

Locally built core and Agent images passed all four fresh-install combinations
(authentication off/on, Agent absent/present), container recreation, and upgrades
from v0.6.0 with and without Agent, followed by enabling authentication. Checks
covered retained topology and saved-device bytes, remembered logins, published
instructions, activity records, Agent draft persistence and login isolation.
Independent browser sessions against the packaged server verified lock handoff,
admin approval, reader restrictions and logout across tabs. Both source and
prebuilt Compose configurations validated across the same option combinations.

A disposable public-export rehearsal passed the file/content/link checks; core
and Agent images rebuilt from that export match the tested candidate images.
Agent automation uses deterministic fixtures and packaged console tests use a
PTY echo device. These checks do not establish real provider sign-in/inference,
native guest forwarding, or an independent security audit.

The release workflow runs backend, browser, MCP and container smoke checks before
publishing the core, EXOS edition and optional Agent images. The GitHub release
is created only after all three image jobs succeed.
